## 一、项目定位与现有功能

### 一句话定位

一个只给两个人用的私密情侣记录 PWA：记录恋爱天数、纪念日、情书、照片、日记、地图打卡等，数据存放在自己租用的服务器上。

### 目标用户与核心场景

| 项目 | 内容 |
|---|---|
| 目标用户 | 情侣双方（当前实际为 2 人），共用同一个登录账号 |
| 核心场景 | 每天打开看恋爱天数；写情书/日记；上传照片；记录纪念日；回顾年度回忆 |
| 使用方式 | 手机浏览器「添加到主屏幕」当 App 用；桌面浏览器直接访问 |
| 数据主权 | 前端静态托管在 GitHub Pages，数据在后端自建 Supabase（腾讯云香港服务器） |

### 用户角色与权限视角

| 角色 | 能做什么 | 边界 |
|---|---|---|
| 未登录访客 | 只能看到登录页 | RLS 拒绝一切数据访问 |
| 登录用户（情侣双方共用同一账号） | 读写本账号的整份数据、上传/删除自己目录下的照片 | 只能访问 `user_id = auth.uid()` 的行；照片目录必须以自己的 UUID 开头 |
| 服务器管理员（root/SSH） | 管理容器、数据库、备份、证书 | 可直接读全部数据；当前**没有端到端加密** |
| GitHub 仓库维护者 | 修改前端并发布 | 不能直接读服务器数据 |

> 重要：系统没有「我 / TA」两套真实身份。情书、留言里的 `author: 'me' | 'partner'` 只是前端自填字段，不是鉴权身份。双方共用账号意味着双方拥有完全相同的数据权限。

## 五、数据库结构及数据导出方式

### 数据库类型与版本

- 类型：PostgreSQL
- 版本：17.6.1.136（Supabase 官方镜像）
- 部署：Docker 容器 `supabase-db`，数据目录为宿主机 bind mount（`/opt/supabase/docker/volumes/db/data`，以实际 `docker inspect` 为准）
- 公网端口：未开放；仅容器网络与宿主机本地访问

### 数据表清单

#### 1. `public.koii_data`（业务主表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | `uuid` | 主键，外键 → `auth.users(id)`，`ON DELETE CASCADE` | 登录账号 ID，一个账号一行 |
| `data` | `jsonb` | `NOT NULL DEFAULT '{}'` | 整份应用数据（见下方 JSONB 结构） |
| `updated_at` | `timestamptz` | `NOT NULL DEFAULT now()` | 最后更新时间 |

| 项 | 内容 |
|---|---|
| 索引 | 主键索引 `koii_data_pkey(user_id)`；无额外自定义索引 |

### API 风格与认证

### 核心业务流程

#### 1. 登录与首次同步

1. 用户输入邮箱密码。
2. 前端调用 GoTrue 登录，拿到 access/refresh token。
3. SDK 将会话写入浏览器 localStorage。
4. 前端调用 `pullData` 拉取 `koii_data` 中 `user_id = auth.uid()` 的行。
5. 若云端有数据，覆盖本地缓存；若云端为空但本地已有数据，则首次上传本地数据。
6. 订阅 Realtime `postgres_changes`，监听本行变更。
7. 顶部状态灯变为「已云同步」。

#### 2. 记录发布/编辑

1. 用户在页面操作，`store.tsx` 更新 React 状态。
2. 状态立即写入 localStorage（离线可看）。
3. 600ms 防抖后，整份 `AppData` upsert 到 `koii_data`。
4. 另一台设备通过 Realtime 收到新行，比较 JSON 后更新本地状态。
5. 双方界面实时一致。

#### 3. 照片上传

1. 用户选择图片。
2. `compressImage` 用 Canvas 压缩到最长边 1080、JPEG 质量 0.8。
3. 上传到 `koii-photos/${userId}/${photoId}.jpg`，`upsert: true`。
4. 返回路径写入 `data.photos[].path`（或日记的 `photos[]`）。
5. 展示时调用 `createSignedUrl` 获取 1 小时链接；前端缓存 50 分钟。

#### 4. 删除与回收站

1. 删除操作把对象移入 `trash`，不立即删除照片文件。
2. 回收站可恢复原对象。
3. 彻底删除时，若为照片/日记，调用 Storage 删除对应文件，再从 `trash` 移除。
4. 「清空所有记录」会重置本地数据并退出登录。

#### 5. 纪念日提醒

1. 应用打开且已完成引导时触发 `fireReminder`。
2. 筛选 7 天内到期的纪念日/生日。
3. 若浏览器已授权通知，弹出系统通知。
4. 用 `localStorage['koii:notified:YYYY-MM-DD']` 保证每天最多一次。
5. 未打开应用时不会提醒（无后台推送）。

#### 6. 情侣「绑定」

- 当前没有绑定流程。双方使用**同一个邮箱密码**登录，即共享同一行数据。
- 这也意味着无法区分谁写了哪条记录（`author` 字段是手动选择）。

### 关键业务规则与边界条件

| 规则 | 说明 |
|---|---|
| 单行模型 | 一个账号只有一行 `koii_data`，整份 JSON 覆盖写入 |
| 并发策略 | **最后写入者获胜（last-write-wins）**，无版本号/乐观锁 |
| 幂等 | `upsert on user_id`，重复推送不会产生多行 |
| 回声抑制 | Realtime 收到自己的推送后，用 `JSON.stringify` 比较，相同则不更新 |
| 权限 | RLS 强制 `auth.uid() = user_id`；Storage 强制目录前缀 |
| 上传大小 | Nginx `client_max_body_size 20m`；前端压缩到 1080px |
| 图片链接 | 签名有效期 3600 秒；前端缓存 50 分钟 |
| 通知频率 | 每天最多一次；仅前台 |
| 备份保留 | 最近 7 天 |
| 注册 | 关闭；仅管理员可建号 |
| 删除账号 | 级联删除 `koii_data`；照片文件不会自动删除（需手工清理） |

5. 备份文件包含个人隐私与最高权限密钥，视同生产密钥管理。

### 技术债

| 项 | 说明 | 建议 |
|---|---|---|
| `store.tsx` 单体过大 | 701 行，承载鉴权、同步、全部 CRUD | 拆分为 auth/sync/CRUD/trash 模块 |
| 无路由 | 无 URL、无深链接、浏览器返回键行为不完整 | 引入轻量路由或 hash 路由 |
| 数据校验宽松 | `normalize()` 只补数组，不校验字段类型 | 引入 zod 等运行时校验 |
| 无迁移框架 | 数据库变更靠手工 SQL | 引入 Supabase CLI migrations |
| 镜像未锁 digest | `docker compose pull` 可能引入非预期升级 | 固定 digest 或版本并记录 |
| 手工发布 | 无 CI/CD、无回滚脚本 | GitHub Actions + 版本化产物 |
| 文档不同步 | README 旧、部署文档部分命令已过时 | 每次变更同步 docs |
| 备份脚本依赖容器名/挂载探测 | 容器改名或挂载变化时可能跳过照片 | 增加失败告警与校验 |
