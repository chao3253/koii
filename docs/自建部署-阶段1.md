# 阶段 1 施工单：在轻量服务器上自建 Supabase

> 目标：把现在的 Supabase（境外托管）整套搬到你自己的一台服务器上。
> 网站代码几乎不用改，登录 / 数据库 / 照片 / 实时同步全部保留。
> 预计耗时：1～2 小时（不含备案）；费用：约 ¥50～100 / 月。
>
> **怎么读这份文档**：每个部分先讲「做什么」，再用 💡 讲「为什么」。
> 命令可以照抄，但建议先花 1 分钟看完 💡，知道自己在干什么，出错时才不会慌。
> 完全没接触过服务器的话，**先读下面的「序章」**，十分钟就能建立整体画面。

## 序章：先搞懂几个大概念（纯小白版）

> 这一章不写命令，只讲「这东西到底是什么、为什么需要它」。
> 看不懂的地方可以先跳过，等做到那一步再回来看，会更容易懂。

### 1. 你打开网站的那一瞬间，发生了什么？

用「点外卖」来类比：

1. 你在浏览器输入 `cz520.online`——这只是个**名字**，机器不认识名字。
2. **DNS** 像通讯录，把名字翻译成一台机器的地址（IP）。
3. 浏览器跑到那个地址，取回一堆**网页文件**（HTML / CSS / JS）。
4. 这些文件在你手机里跑起来，变成你看到的按钮、照片墙、动画。
5. 但日记、照片、登录状态**不在**网页文件里，它们住在**后端**，网页还要再向后端要一次数据。

所以一次打开网站，背后至少有两段旅程：**取网页** 和 **取数据**。

### 2. 一个网站 = 前端 + 后端

用「餐厅」来类比：

- **前端** = 门面、菜单、装修。所有客人看到的都一样，可以印很多份、随便发。
  技术上它就是一堆静态文件，放在任何「展示柜」里都行——GitHub Pages 就是这样一个免费展示柜。
- **后端** = 厨房、仓库、收银台。只有一个，负责做菜（处理数据）、保管食材（存照片）、核对会员身份（登录）。

**关键区别**：前端可以到处复制，后端不行。后端里存着你们唯一的那份回忆，所以它需要一个稳定的地方。

### 3. 服务器是什么？

**服务器就是一台一直开着、连着互联网、有固定门牌号的电脑。**

它和你的笔记本没有本质区别，只是：

| | 你的电脑 | 服务器 |
|---|---|---|
| 开关机 | 用完就关 | 24 小时开着 |
| 门牌号 | 家庭宽带 IP 经常变 | 固定公网 IP |
| 网络 | 上行带宽小 | 带宽大、上下行对等 |
| 环境 | 放在家里 | 放在机房，有电、有网、有空调、有人值守 |

它不需要显示器、键盘、鼠标——你通过 SSH 远程登录进去操作，就像用一条加密的远程桌面。

> 类比：你想开一家店。可以选「在自家客厅接客」（家用电脑），也可以选「租一间 24 小时营业的临街店面」（服务器）。前者省钱但客人进不来、你一关灯就停业；后者要付租金，但随时能开门。

### 4. 为什么是「租」而不是「买」？

你买的其实不是一台实体机器，而是**机房里的一小块空间**（虚拟机 / 容器）。
云厂商把一台大服务器切成很多份，租给不同的人。

- 按月付租金，配置随时升降
- 机器坏了厂商换，不用你修硬件
- 不用了随时退，不用处理旧设备

> 类比：租房 vs 买地盖楼。你现在只需要一间能开门的店，不需要先买一块地。

### 5. 那为什么「你这个项目」需要服务器？

现在的架构是这样的：

- **前端**：住在 GitHub Pages（免费展示柜，没问题）
- **后端**：借住在 Supabase（别人家的仓库，而且这仓库在境外）

借住的问题有三个：

1. **绕远路**：数据要跨越半个地球，国内访问慢、偶尔不稳
2. **有限制**：免费额度有上限，项目 7 天不用会休眠
3. **钥匙不在自己手里**：数据、登录、照片都存在别人家

自建服务器，就是**自己租一间仓库，把后端搬进去**。房子还是租的，但钥匙在自己手里。

### 6. 服务器里到底装了什么？

你可以把这次部署想象成「装修一间空房」：

| 要装的东西 | 它是什么 | 类比 |
|---|---|---|
| Ubuntu | 操作系统 | 房子的地基和墙 |
| Docker | 容器工具 | 集装箱吊车，把家具打包搬进去 |
| Supabase | 后端全家桶 | 家具：数据库、登录、照片仓库、实时推送 |
| Nginx | 反向代理 | 门卫 + 前台，负责 HTTPS 和指路 |
| Certbot | 证书工具 | 帮你免费办「网站身份证」 |

你要做的不是「造家具」，而是「把家具搬进去、接上水电」。这就是为什么施工单里的命令看起来多，但每一步都不难。

### 8. 难度分级：哪些必须懂，哪些了解即可

后面的 💡 会用三个标记：

- 🟢 **必懂**：服务器、前端/后端、域名、HTTPS、备份。这些直接关系到「网站能不能用、数据会不会丢」。
- 🟡 **了解即可**：Docker、RLS、JWT、反向代理、WebSocket。知道「它是干嘛的、出问题看哪里」就够了，不用会推导。
- 🔴 **深水区，先跳过**：加密握手细节、容器内核隔离、数据库索引原理、JWT 签名算法。这些是专业运维和开发才需要深入的，你现在**照着做就行**。

**原则：先跑通，再理解。** 很多概念是做一遍之后自然就懂的，不用提前啃书本。

### 9. 给小白的三条心态

1. **报错是正常的**，不是你的问题。把报错原文贴出来，绝大多数都能定位。
2. **不跳步**。每一步都有检查点，过了再走下一步；跳步省下的十分钟，往往要花一小时补。
3. **深水区可以先「会用」**。就像开车不需要懂发动机原理，先能上路，兴趣会带你慢慢深入。

## 0. 开始前，你需要准备

- [ ] 一台轻量应用服务器（腾讯云 / 阿里云都行）
- [ ] 服务器公网 IP、root 密码（或密钥）
- [ ] 域名 `cz520.online` 的解析权限（在阿里云域名控制台）
- [ ] 旧站（现网 Supabase）还能正常登录，用于迁移数据

**先别动旧站**：新站跑通、数据核对无误之前，旧站一直保持在线。

> 💡 **为什么先别动旧站？**
> 搬家最怕的是「新家还没收拾好，旧家已经退了」。
> 自建服务器涉及网络、证书、数据库、存储好几个环节，任何一个出问题都可能让网站暂时打不开。
> 旧站留着，就等于留了一条随时能退回去的路——这在工程上叫**回滚（rollback）**。
> 真正靠谱的迁移，永远是「先建新的 → 验证 → 再拆旧的」。

## 1. 买服务器

推荐配置（个人项目足够）：

| 项目 | 建议 |
|---|---|
| 机型 | 轻量应用服务器 |
| 配置 | **2 核 4G**（Supabase 全家桶吃内存，2G 会 OOM） |
| 系统盘 | 60GB 以上 |
| 带宽 | 3～5 Mbps，或按流量计费 |
| 镜像 | **Ubuntu 22.04 LTS** |
| 地域 | 先选 **香港 / 境外**（免备案，先跑通） |

安全组 / 防火墙只开放三个端口：

- `22`（SSH）
- `80`（HTTP，申请证书用）
- `443`（HTTPS）

> 8000 端口**不要**对公网开放，后面用 Nginx 转发 + SSH 隧道访问后台。

> 💡 **为什么是这些配置？**
>
> **为什么要 4G 内存？** 你以为只装了一个 Supabase，其实它是一整套服务拼起来的：
> 数据库（Postgres）、登录（Auth）、文件存储（Storage）、实时推送（Realtime）、
> API 网关（Kong）、网页后台（Studio）……每个都要占内存。
> 2G 跑起来会频繁「内存不够杀进程」，表现就是容器反复重启、网站时好时坏。
> 4G 是舒服的起步线，加 2G swap 是保险。
>
> **为什么选「轻量应用服务器」而不是「ECS / 云服务器」？**
> 轻量 = 套餐化，CPU、内存、带宽、流量打包好，便宜、开箱即用，适合个人项目；
> ECS = 零件化，什么都能自定义，但更贵、更复杂。你们这个量级，轻量完全够。
>
> **为什么先选香港？** 这就要说到**备案**了。
> 中国大陆的服务器要绑定域名，必须先向工信部做 **ICP 备案**，否则 80/443 端口会被拦。
> 备案要提交身份资料、等 2～4 周；而且**个人备案不能做社交、相册、论坛类内容**，
> 你们这种双人私密空间有可能被要求走企业备案。
> 香港和境外节点不在这个管辖范围内，**免备案**，适合先把技术流程跑通。
> 等整套玩熟了，再决定要不要迁回国内、要不要折腾备案。
>
> **为什么只开 22 / 80 / 443？**
> 端口就像一栋楼里的一扇扇门。开得越多，能被人尝试推开的门就越多。
> 22 是远程登录（你进门用的），80/443 是网站（访客进门用的），其余一律关死。
> 少开一扇门，就少一类被扫描、被爆破的风险。
>
> **带宽和流量有什么区别？**
> 带宽是「水管有多粗」（同时能跑多快），流量是「这个月用了多少水」。
> 轻量服务器一般给一个月度流量包，用超了会限速或额外计费——照片看得多时要留意。

## 2. 第一次登录 + 基础安全

```bash
ssh root@你的服务器IP
```

```bash
# 更新系统
apt update && apt upgrade -y

# 设置时区
timedatectl set-timezone Asia/Shanghai

# 加 2G swap（4G 内存也建议加，防止构建时 OOM）
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 确认内存和 swap
free -h
```

**创建日常用户（不要一直用 root）：**

```bash
adduser koii
usermod -aG sudo koii
```

把本机的 SSH 公钥放到服务器（可选但强烈推荐）：

```bash
# 在你自己电脑上执行（不是服务器）
ssh-copy-id koii@你的服务器IP
```

然后编辑 `/etc/ssh/sshd_config`，确认：

```
PasswordAuthentication no
PermitRootLogin no
```

```bash
systemctl restart ssh
```

**防火墙：**

```bash
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
ufw status
```

> ⚠️ 云厂商控制台的「安全组」和服务器里的 `ufw` 是两层，两个都要放行。

> 💡 **为什么一上来就折腾安全？**
>
> **root 是什么？** 是 Linux 的超级管理员，权限最大，什么都能删。
> 也正因为如此，它是全网自动化脚本最喜欢爆破的账号——互联网上每天都有人在扫 22 端口。
> 日常用一个普通账号（`koii`），需要管理员权限时再 `sudo`，就算这个账号被盗，损失也小得多。
>
> **SSH 密钥为什么比密码安全？** 密码可以猜、可以撞库；密钥是一对数学上配对的字符串，
> 私钥留在你电脑里、公钥放服务器上，**几乎不可能被暴力破解**。关掉密码登录后，爆破脚本直接失效。
>
> **swap 是什么？** 是拿硬盘划出来的一块「备用内存」。内存不够时，系统把不常用的数据临时挪到硬盘上，
> 慢一点，但不会直接崩溃。对自建 Supabase 这种内存敏感的服务，是性价比极高的保险。
>
> **为什么防火墙有两层？** 云厂商的「安全组」在机房网络层拦截，`ufw` 在服务器系统层拦截。
> 两层都配，等于大楼门禁 + 自家门锁，任何一层漏了还有另一层兜底。

## 3. 安装 Docker

```bash
sudo apt install -y ca-certificates curl git
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER
```

退出重新登录，然后验证：

```bash
docker --version
docker compose version
```

> 国内服务器拉镜像慢的话，可以给 Docker 配镜像加速（腾讯云/阿里云控制台都有现成的加速地址）。香港节点一般不需要。

> 💡 **Docker 到底解决了什么问题？**
>
> 想象你要装 Supabase：它需要特定版本的 Postgres、Node、Python、Go 运行时，
> 还要配一堆环境变量和网络。手动装，就像照着菜谱从磨面粉开始做蛋糕——
> 换个系统、换个版本，配方就全变了，这就是臭名昭著的**依赖地狱**。
>
> Docker 把「程序 + 它需要的一切」打包成一个**镜像（image）**，像集装箱一样，
> 到哪里都能原样运行。镜像跑起来就是**容器（container）**。
> 一台服务器上可以同时跑十几个互不干扰的容器。
>
> **docker compose** 则是「集装箱码头调度单」：一个配置文件写清楚要跑哪些容器、
> 谁连谁、端口怎么映射，一条命令全部拉起。Supabase 官方就是这么交付的。
>
> 你不需要成为 Docker 专家，先记住三个词：**镜像 = 模板，容器 = 运行中的实例，compose = 批量编排**。

## 4. 部署 Supabase

```bash
cd /opt
sudo git clone --depth 1 https://github.com/supabase/supabase
sudo chown -R $USER:$USER /opt/supabase
cd /opt/supabase/docker
cp .env.example .env
```

### 4.1 生成密钥

先生成一个 JWT 密钥：

```bash
openssl rand -base64 48
```

把输出保存下来，记为 `JWT_SECRET`。然后用它生成 `ANON_KEY` 和 `SERVICE_ROLE_KEY`（本机 python3 直接跑，无需装包）：

```bash
export JWT_SECRET='把上面生成的密钥粘贴到这里'
python3 - <<'PY'
import base64, hmac, hashlib, json, time, os

secret = os.environ["JWT_SECRET"]

def b64(b):
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

def make(payload):
    header = {"alg": "HS256", "typ": "JWT"}
    h = b64(json.dumps(header, separators=(",", ":")).encode())
    p = b64(json.dumps(payload, separators=(",", ":")).encode())
    sig = b64(hmac.new(secret.encode(), f"{h}.{p}".encode(), hashlib.sha256).digest())
    return f"{h}.{p}.{sig}"

iat = int(time.time())
exp = iat + 60 * 60 * 24 * 365 * 10
print("ANON_KEY=" + make({"role": "anon", "iss": "supabase", "iat": iat, "exp": exp}))
print("SERVICE_ROLE_KEY=" + make({"role": "service_role", "iss": "supabase", "iat": iat, "exp": exp}))
PY
```

### 4.2 编辑 `.env`

```bash
nano .env
```

按下面这些项修改（变量名以你拉到的 `.env.example` 为准）：

| 变量 | 填什么 |
|---|---|
| `POSTGRES_PASSWORD` | 自己生成一串长随机密码 |
| `JWT_SECRET` | 上面生成的 `JWT_SECRET` |
| `ANON_KEY` | 上面生成的 `ANON_KEY` |
| `SERVICE_ROLE_KEY` | 上面生成的 `SERVICE_ROLE_KEY` |
| `DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD` | 后台登录账号密码，自己定 |
| `SECRET_KEY_BASE` | `openssl rand -base64 48` 再生成一个 |
| `VAULT_ENC_KEY` | `openssl rand -hex 16` |
| `SITE_URL` | `https://cz520.online` |
| `API_EXTERNAL_URL` | `https://api.cz520.online` |
| `ENABLE_EMAIL_AUTOCONFIRM` | `true`（没配 SMTP 时，注册后直接可用） |
| `DISABLE_SIGNUP` | 先 `false`，建好账号后改 `true` |

保存后收紧权限：

```bash
chmod 600 .env
```

> 🔐 `SERVICE_ROLE_KEY` 是最高权限密钥，**只放在服务器 `.env` 里**，不要发给任何人、不要写进前端代码。

### 4.3 启动

```bash
sudo docker compose up -d
sudo docker compose ps
```

全部 `running` / `healthy` 即成功。第一次拉镜像会比较久。

**检查点 ✅**：`curl -s http://127.0.0.1:8000/auth/v1/health` 返回 JSON。

> 💡 **这一节的名词，一次讲明白**
>
> **Supabase 自托管到底装了什么？** 一整套集装箱：
> - `db`：PostgreSQL 数据库，数据真正住的地方
> - `auth`（GoTrue）：注册、登录、发令牌
> - `rest`（PostgREST）：把数据库表自动变成 API
> - `storage`：照片文件仓库
> - `realtime`：数据一变就推送给另一台设备
> - `kong`：大门，所有请求先经过它再分发给内部服务
> - `studio`：网页版后台，看数据、跑 SQL、建用户
>
> 🔴 **JWT 是什么？**（深水区，了解即可）一张「带签名的通行证」。服务器用自己的密钥签个名，之后看到签名就知道这张证是真的、没被改过。
> 它长得像 `xxxxx.yyyyy.zzzzz` 三段：头部、内容、签名。
>
> **anon 和 service_role 有什么区别？** 这是最关键的一对概念：
> - `ANON_KEY`：给**前端网页**用的，权限受 RLS 限制，只能看自己那行数据。**可以公开**。
> - `SERVICE_ROLE_KEY`：**绕过所有 RLS**，等于数据库的万能钥匙。**绝对不能公开**，只留在服务器上。
>
> **`.env` 是什么？** 一个纯文本配置文件，集中放密码和密钥。
> 程序启动时读它，就不用把密钥写死在代码里。`chmod 600` 表示「只有文件主人能读」，
> 防止服务器上其他账号偷看。
>
> **为什么要 `ENABLE_EMAIL_AUTOCONFIRM`？** 正常注册会发一封验证邮件，但自建环境默认没有邮件服务器（SMTP），
> 邮件发不出去，账号就永远「未验证」。打开这个开关，注册后直接可用；
> 你们只有两个人，建好账号后再把注册关掉，反而更安全。

## 5. 初始化数据库

### 5.1 安全地打开后台（SSH 隧道）

不要对公网开 8000。在你自己的电脑上执行：

```bash
ssh -L 8000:127.0.0.1:8000 koii@你的服务器IP
```

保持这个窗口不动，浏览器打开 `http://localhost:8000`，用 `.env` 里的后台账号登录。

> 后台地址以你拉到的版本 README 为准（有的版本是 8000，有的通过 Kong 路由）。

### 5.2 跑建表脚本

后台 → **SQL Editor** → 粘贴项目里的 `supabase/schema.sql` 全文 → Run。

它会创建：

- `koii_data` 表 + 4 条 RLS 策略
- Realtime 发布
- 私有存储桶 `koii-photos` + 3 条存储策略

### 5.3 建登录账号

后台 → **Authentication → Users → Add user**：

- 邮箱：你们共用的那个
- 密码：你们的密码
- 勾选 **Auto Confirm User**

建好后回到 `.env`，把 `DISABLE_SIGNUP` 改成 `true`，重启：

```bash
sudo docker compose up -d
```

**检查点 ✅**：Users 列表里能看到账号，且状态是 confirmed。

> 💡 **数据库、RLS、存储桶，到底是什么？**
>
> **表 / 行 / 列**：数据库像一张 Excel。`koii_data` 是表名，每一行是一个用户的数据，
> 列是 `user_id`、`data`、`updated_at`。
>
> 🟡 **为什么你们的数据只占一行 JSON？** 因为这是个「以设备为中心」的应用：
> 前端把整份数据（日记、照片索引、纪念日……）当成一个文档，改完整体推上去。
> 好处是简单、灵活，加新功能不用改表结构；代价是**两个人同时改，可能后写的覆盖先写的**。
> 对两个人的使用频率来说，冲突概率很低，实时同步也能让双方尽快看到最新状态。
> 如果以后要做「多人协作」，才需要拆成更细的表。
>
> 🟡 **RLS 是什么？** Row Level Security，行级安全。它把「哪一行能被谁看见」写进数据库本身：
> 每条策略都在说「只有 `auth.uid() = user_id` 才允许读写」。
> 所以就算前端密钥公开、有人拿到你的 anon key，**没有登录就拿不到任何一行数据**。
> 这正是「anon key 可以公开」的底气。
>
> **存储桶是什么？** 数据库擅长存文字，不适合塞几 MB 的照片。
> 存储桶（bucket）就是专门放文件的「云盘目录」。我们把桶设为**私有**，
> 前端只能拿到一个**限时签名链接**（默认 1 小时）来显示照片，过期自动失效。
>
> **为什么后台只走 SSH 隧道？** Studio 后台等于「总控制室」，能看能改所有数据。
> 如果直接暴露在公网，会被全网扫描器盯上。SSH 隧道的意思是：
> 先加密登录服务器，再从服务器内部访问 8000——外人根本看不到这扇门。

## 6. 配 HTTPS 域名

### 6.1 域名解析

在阿里云域名控制台加一条 A 记录：

| 主机记录 | 类型 | 值 |
|---|---|---|
| `api` | A | 你的服务器 IP |

得到 `api.cz520.online`。等 1～10 分钟生效：

```bash
ping api.cz520.online
```

### 6.2 Nginx + 证书

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
```

新建 `/etc/nginx/sites-available/koii-api`：

```nginx
server {
    listen 80;
    server_name api.cz520.online;

    # 照片上传，留足体积
    client_max_body_size 20m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        # Realtime 需要 WebSocket
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 大文件/长连接
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

启用并申请证书：

```bash
sudo ln -s /etc/nginx/sites-available/koii-api /etc/nginx/sites-enabled/
sudo nginx -t
sudo systemctl reload nginx
sudo certbot --nginx -d api.cz520.online
```

**检查点 ✅**：

```bash
curl https://api.cz520.online/auth/v1/health
```

返回 JSON 即 HTTPS 正常。

> 💡 **域名、DNS、HTTPS、反向代理，一条线讲清楚**
>
> **域名和 DNS**：`api.cz520.online` 只是给人看的名字，机器只认 IP。
> DNS 就是「通讯录」，A 记录把名字翻译成 IP。改解析 = 改通讯录，通常几分钟到几小时生效。
>
> **HTTP 和 HTTPS**：HTTP 是明文寄明信片，路上谁都能看、能改；
> HTTPS 是给信封上锁，传输内容加密。你们的照片、密码、情书，必须走 HTTPS。
>
> **证书是什么？** 一张「网站身份证」，由受信任的机构签发，同时提供加密用的公钥。
> Let's Encrypt 免费签发，有效期 90 天，certbot 会自动续期——所以不用怕过期。
> 注意：证书是签给**域名**的，不是签给 IP 的，所以必须先有域名解析。
>
> **反向代理是什么？** Nginx 站在门口当接待员：访客只看到 443 端口，
> 它把请求转给里面 8000 端口的 Kong，再把结果送出去。
> 好处是：内部服务不用直接暴露、可以统一做 HTTPS、限流、缓存。
>
> 🟡 **为什么 Nginx 配置里要写 `Upgrade`？** 实时同步用的是 **WebSocket**——
> 一条一直开着的双向通道，服务器有变化能立刻推给手机。
> 普通代理默认只处理「一问一答」，不转发 `Upgrade` 头，WebSocket 就建不起来，
> 表现就是「数据能存，但另一台设备不刷新」。这是自建最常见的坑之一。
>
> **`client_max_body_size` 是什么？** 允许上传的最大体积。默认只有 1MB，
> 手机照片压缩后也可能超过，不改就会报 413（请求体过大）。

### 上线前自测清单

- [ ] 能登录（用第 5.3 步建的账号）
- [ ] 首页数据能保存，刷新后还在
- [ ] 照片墙能上传、能显示、能放大、能保存到手机
- [ ] 时光手账能写日记、加照片
- [ ] 手机和电脑同时打开，改一条数据，另一边几秒内自动更新（Realtime）

> 💡 **前端和后端，到底谁是谁？**
>
> 你们看到的网页（按钮、照片墙、动画）是**前端**，它本质是一堆 HTML/CSS/JS 文件，
> 可以放在任何静态托管上（GitHub Pages、OSS、Nginx）。
> 数据、登录、照片文件在**后端**。前端通过 `https://api.cz520.online` 找后端要数据。
>
> 所以「换后端」只需要改一个地址，前端代码几乎不动——这也是当初选 Supabase 这种
> 「前后端分离」架构的好处：两边可以各自搬家。
>
> **anon key 为什么可以写在前端代码里？** 因为它只是「访客通行证」，
> 真正拦人的是数据库里的 RLS。没有登录，拿着 anon key 也只能看到空气。
> 但 `SERVICE_ROLE_KEY` 是万能钥匙，**绝不能**出现在前端。
>
> **为什么自测要测「未登录看不到数据」？** 这是验证 RLS 真的生效。
> 如果未登录也能看到，说明策略配错了，必须马上修。

## 8. 数据迁移（旧站 → 新站）

> 顺序很重要：先迁文字，再迁照片，最后核对。

### 8.1 文字数据

1. 旧站 → 设置 → **导出备份**，得到 `koii-backup-xxx.json`
2. 新站 → 用同一账号登录 → 设置 → **导入备份**
3. 打开首页 / 时光 / 照片墙核对数量

### 8.2 照片文件

照片在存储桶里，路径必须是 `用户ID/文件名.jpg`，**路径不能变**，否则数据库里记录的照片找不到。

两种办法：

- **A. 我来写迁移脚本**（推荐）：用旧站账号登录后，脚本列出并下载所有照片，再上传到新站。需要你在本地跑一次，密钥不经过任何第三方。
- **B. 手动**：旧站 Storage 里逐个下载 → 新站 Storage 上传到同样的 `${userId}/` 目录下。

> 注意：新站登录后的 `用户ID` 和旧站可能不同（自建库重新建号）。
> 如果不同，需要把 JSON 里的 `path` 前缀批量替换成新 ID，或者直接在新库用**相同的 UUID** 建账号。
> 这一点迁移前我会帮你确认，别自己硬改。

### 8.3 切换与回滚

- 前端指向新后端、自测通过后，观察 1～2 天
- 旧站先别删，作为回滚方案
- 确认无误后再停用旧 Supabase 项目

**检查点 ✅**：新站的照片数量、日记数量、总记录数和旧站一致。

> 💡 **为什么照片要单独搬？**
>
> 你们的数据其实住在**两个地方**：
> - 数据库：文字（日记内容、纪念日、照片的「地址」）
> - 存储桶：照片文件本身
>
> 数据库里存的不是照片，而是「照片住在哪」这个路径，比如 `用户ID/abc.jpg`。
> 所以搬家时，**文件要放到一模一样的路径**，数据库里的地址才找得到。
> 只搬数据库不搬文件，照片墙会全是裂图；只搬文件不搬数据库，页面根本不知道有这些照片。
>
> **用户 ID 为什么关键？** 路径的第一段就是用户 ID。
> 自建库重新建账号时，系统会生成一个新的 UUID；如果和旧站不一样，
> 所有照片路径的前缀都对不上。解决办法有两个：在新库用**相同的 UUID** 建账号（最省事），
> 或者批量替换 JSON 里的路径前缀。前者更安全，后者容易漏。
>
> **为什么要观察 1～2 天再删旧站？** 有些问题不会立刻暴露，比如：
> 半夜备份失败、证书续期异常、某张老照片路径不对。
> 留一条退路，成本几乎为零，价值却很大。

## 9. 备份（最重要的一步，别跳过）

新建 `/opt/backup/backup.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail

cd /opt/supabase/docker
STAMP=$(date +%F)
mkdir -p /opt/backup

# 数据库
sudo docker compose exec -T db pg_dump -U postgres -d postgres \
  | gzip > /opt/backup/db-$STAMP.sql.gz

# 照片（卷名用 docker volume ls 确认，通常带项目前缀）
sudo docker run --rm \
  -v supabase_storage_data:/data:ro \
  -v /opt/backup:/backup \
  alpine tar czf /backup/storage-$STAMP.tar.gz -C /data .

# 只保留最近 7 天
find /opt/backup -name '*.gz' -mtime +7 -delete
```

```bash
chmod +x /opt/backup/backup.sh
sudo /opt/backup/backup.sh
ls -lh /opt/backup
```

加到定时任务：

```bash
sudo crontab -e
```

```cron
17 3 * * * /opt/backup/backup.sh >> /var/log/koii-backup.log 2>&1
```

**再加一层异地备份**（强烈建议）：把 `/opt/backup` 同步到阿里云 OSS 或你的网盘（rclone 支持两者）。服务器坏了，备份还在。

**每月做一次恢复演练**：把备份解压到临时目录、导入一个测试库，确认能恢复。

**检查点 ✅**：`/opt/backup` 里有当天的 `db-*.sql.gz` 和 `storage-*.tar.gz`。

> 💡 **备份的黄金法则：3-2-1**
>
> - **3 份**数据：生产一份 + 本地备份一份 + 异地一份
> - **2 种**介质：服务器硬盘 + 对象存储/网盘
> - **1 份**在异地：机房着火、服务器被删，异地那份还在
>
> **为什么备份一定要「演练恢复」？** 没恢复过的备份，只能叫「文件」，不能叫「备份」。
> 常见翻车现场：备份脚本每天成功，但备份出来的是空文件；或者恢复时发现版本不兼容。
> 每月花十分钟真的恢复一次，才能确认它是活的。
>
> 🟡 **`pg_dump` 和「快照」有什么区别？**
> `pg_dump` 是**逻辑备份**：把数据导出成 SQL 语句，跨版本、跨机器都能导入，体积小。
> 云厂商的「磁盘快照」是**物理备份**：整块硬盘拍照，恢复快，但通常只能在同平台用。
> 个人项目，`pg_dump` + 照片打包已经足够；快照可以作为额外一层。
>
> **为什么只留 7 天？** 备份文件会一直变大，磁盘满了反而会让服务挂掉。
> 7 天足够覆盖「误删几天后才发现」的场景。重要节点可以每月手动留一份长期归档。

## 10. 费用与监控

- [ ] 云控制台设置**费用预警**（例如每月 ¥100 短信/邮件提醒）
- [ ] 开启服务器监控告警（CPU、内存、磁盘）
- [ ] 开启系统自动安全更新：`sudo apt install unattended-upgrades`
- [ ] 每月看一次账单，确认没有意外流量费

> 轻量服务器的流量包用完后会限速或按量计费，照片多、看得多时要留意。

> 💡 **为什么一定要设费用预警？**
>
> 云服务的计费方式比话费复杂：服务器本身包月，但**流量、快照、对象存储、公网 IP**
> 往往是按量另算的。一个配置失误（比如被爬虫疯狂下载照片），账单可能在几天内涨起来。
> 费用预警不是省钱技巧，是**止损开关**——超过阈值先收到通知，你才有时间处理。
>
> **自动安全更新是什么？** 系统和软件会不断被发现漏洞，厂商发布补丁。
> `unattended-upgrades` 让服务器自动装安全补丁，减少「因为忘了更新被入侵」的概率。
> 注意它一般只装安全更新，不会乱升大版本。

## 11. 常见坑

| 现象 | 原因 / 解决 |
|---|---|
| 容器反复重启 | 内存不够，升到 4G 或加 swap |
| 照片上传 413 | Nginx 的 `client_max_body_size` 太小 |
| 实时同步不生效 | Nginx 没转发 WebSocket 的 `Upgrade` / `Connection` 头 |
| 注册后登录不了 | 没配 SMTP，需开 `ENABLE_EMAIL_AUTOCONFIRM` 或后台手动确认 |
| 浏览器报 CORS | 检查 Kong 的 CORS 配置，允许 `https://cz520.online` |
| 后台打不开 | 8000 没对公网开放是**正常的**，用 SSH 隧道访问 |
| 磁盘越用越满 | 旧镜像/日志堆积，`docker system df` 查看，谨慎清理 |
| 证书到期 | certbot 会自动续期，`sudo certbot renew --dry-run` 验证 |

> 💡 **遇到问题时的通用排查顺序**
>
> 1. **先看日志**：`sudo docker compose logs --tail=100 服务名`
> 2. **再看状态**：`sudo docker compose ps`，有没有容器在重启
> 3. **再看资源**：`free -h`、`df -h`，内存/磁盘是不是满了
> 4. **最后看网络**：`curl` 本地端口通不通，再试域名
>
> 90% 的问题都能被这四步定位。把报错**原文**贴出来，比描述「打不开」有用一百倍。

## 13. 下一步（阶段 2 预告）

阶段 1 跑稳后，再逐块替换成托管服务，每块都能独立回滚：
